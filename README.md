# Orchestrator

Локальное приложение для запуска очередей задач через Codex CLI. Вы задаёте
задачи, зависимости, разрешённые файлы и проверки в YAML, а Orchestrator
выполняет работу и показывает ход запуска в браузере или Windows-приложении.

Каждая задача запускается в отдельной сессии `codex exec --ephemeral`.
Результаты проверок, ревью, логи и расход токенов сохраняются в истории запуска.

[Быстрый старт](#быстрый-старт) · [Работа с очередями](#работа-с-очередями) ·
[Управление запуском](#управление-запуском) · [Документация](#документация)

## Что умеет

- Выполняет задачи с учётом зависимостей и ограничений на изменение файлов.
- Запускает объявленные проверки, независимое ревью и цикл исправлений.
- Позволяет приостановить очередь, отменить запуск или повторить задачу.
- Последовательно запускает несколько заранее подготовленных очередей.
- Показывает историю, логи и расход токенов по задачам.
- В Control Plane показывает изменения, инциденты, аудит и сводки результатов.

## Быстрый старт

Понадобятся Node.js с npm, Git и доступный Codex CLI с настроенным доступом.
Команды ниже выполняются из корня репозитория Orchestrator.

```powershell
npm install
npm run dev
```

Откройте **[localhost:4317](http://localhost:4317)** — это интерфейс разработки.
API работает на порту `4318`.

Сервер принимает подключения только на `127.0.0.1`. Интерфейс автоматически
получает токен локальной сессии для управляющих запросов; после перезапуска
сервера устаревшая сессия требует повторного действия пользователя. Запросы с
посторонним Host или Origin отклоняются. `npm run dev` отдельно разрешает
локальный интерфейс разработки на порту `4317`.

1. Выберите целевой репозиторий.
2. Загрузите YAML очереди или вставьте его в интерфейс.
3. Проверьте результат предварительной проверки и запустите очередь.
4. Следите за задачами, проверками и ревью в панели запуска.

Для запуска собранного интерфейса:

```powershell
npm start
```

Эта команда сама выполняет сборку. Приложение доступно по адресу
**[localhost:4318](http://localhost:4318)**, если переменная `PORT` не переопределена.

### Windows-приложение

Чтобы собрать установщик:

```powershell
npm run desktop:dist
```

Результат сборки находится в `release/`. Повторный запуск установленного
приложения открывает уже существующее окно. Пока приложение открыто, оно
уведомляет о завершении, ошибке или отмене наблюдаемой очереди.

Orchestrator автоматически предпочитает CLI из установленного Codex Desktop.
Для выбора другого бинарного файла задайте `CODEX_BIN` перед запуском:

```powershell
$env:CODEX_BIN = 'C:\path\to\codex.exe'
npm start
```

## Работа с очередями

### Выберите формат

| Что нужно сделать | Как запускать |
| --- | --- |
| Одну ограниченную задачу | В текущей сессии Codex, без очереди |
| Две или более задачи с известными границами | YAML очереди по [tasks.example.yaml](tasks.example.yaml) |
| Несколько готовых очередей друг за другом | План по [queues.plan.example.yaml](queues.plan.example.yaml) |

Пользовательские очереди и планы храните в `queues/` в корне этого репозитория.
Каталог исключён из Git. Примеры в корне — шаблоны: перед запуском адаптируйте
пути, задачи, разрешения и команды проверок к целевому проекту.

### Подготовьте задачи

До создания очереди должны быть понятны ожидаемый результат каждой задачи,
полный список затрагиваемых файлов и способ проверки результата.
Проверки корректности изменения входят в ту же задачу, что и реализация.

| Поле | Назначение |
| --- | --- |
| `project.path` | Путь к целевому репозиторию |
| `key` | Уникальный ключ задачи |
| `dependsOn` | Ключи непосредственных предшественников |
| `allowedPaths` | Разрешённые пути; `[]` означает только чтение |
| `verificationCommands` | Команды проверки результата |
| `limits.maxParallelTasks` | Лимит одновременного исполнения |

**Для обычной очереди используйте `limits.maxParallelTasks: 1`.** Задачи работают
в общем рабочем дереве. Параллельный запуск допустим только при изолированных
управляемых рабочих пространствах для всех одновременно выполняемых задач.

Разрешённые пути задаются точным путём или каталогом с суффиксом `/**`,
например `src/app.ts` или `server/**`. Шаблоны вида `docs/**/*.md` не поддерживаются.
Обязательные проверки требуют включённого контракта авторизации; пример его
оформления есть в шаблоне очереди.

На Windows команды с PowerShell-переменными и логикой в YAML начинайте с `&`.
Для Python используйте `& $env:PYTHON_BIN ...`. Полные правила, включая
изоляцию pytest и контракты авторизации, — в [техническом справочнике](docs/readme-reference.md#task-format).

### Объедините готовые очереди в план

```yaml
queues:
  - file: queues/01-implementation.yaml
  - file: queues/02-follow-up.yaml
```

Это пример структуры плана: оба файла нужно подготовить заранее.
Относительные пути отсчитываются от каталога, из которого запущен Orchestrator.
Перед стартом проверяются все очереди плана. Следующая начинается только после
успешного завершения предыдущей; ошибка, тайм-аут или отмена останавливает план.

К активной или приостановленной очереди можно добавить следующую через
**Add YAML after current**. Загруженный YAML сразу проходит проверку.

## Управление запуском

| Действие | Результат |
| --- | --- |
| **Pause** | Новые задачи не стартуют; активные завершаются перед переходом в паузу |
| **Cancel** | Активные процессы Codex завершаются, очередь останавливается |
| **Skip** | Активная задача пропускается, зависимые задачи блокируются |
| **Retry** | Создаётся новый запуск с повтором выбранной задачи и сбросом её зависимых задач |
| **Resume** | Создаётся новый запуск для незавершённых задач с учётом зависимостей |

**Retry и Resume используют сохранённый снимок задач и разрешений.** Если вы
исправили YAML, загрузите его как новую очередь: повтор старого запуска
не подхватит изменения файла.

Нажмите название задачи, чтобы открыть её в инспекторе. Для остановленных задач
показаны причина, следующий шаг и исходные доказательства; при блокировке
зависимостью можно перейти к задаче-предшественнику. Неизвестная причина явно
требует диагностики. Ошибки предварительной проверки остаются под редактором
до следующей проверки или изменения YAML.

История и логи по умолчанию находятся в `.orchestrator/runs/`, а каноническая
запись запуска — в `.orchestrator/runs/<run-id>/run.json`. Каталог данных можно
переопределить через `ORCHESTRATOR_DATA_DIR`. Контрольные коммиты задач включаются
настройкой `git.checkpointCommits: true`.

В разделе **«Расход»** можно выбрать запуск и задачу, посмотреть входные
и выходные токены, данные кеша и число вызовов. Стоимость по тарифам провайдера
из этих данных автоматически не вычисляется.

## Разработка

| Команда | Назначение |
| --- | --- |
| `npm run dev` | Сервер и интерфейс с обновлением при изменении исходников |
| `npm run check` | Проверка TypeScript |
| `npm test` | Все автоматически найденные тесты; тот же набор запускается в CI |
| `npm run test:stage1` | Тематические проверки Stage 1 |
| `npm run build` | Проверка TypeScript и сборка интерфейса |
| `npm start` | Сборка и запуск локального сервера |
| `npm run desktop:dist` | Сборка Windows-установщика |

`node scripts/test-all.mjs --list` показывает найденные файлы `*.test.*` и
`*.spec.*`. Сгенерированные каталоги, зависимости, данные запусков и `queues/`
исключены. Два чувствительных к ресурсам Windows-теста выполняются отдельно;
ошибки не скрываются автоматическими повторными попытками.

Локальным HTTP-клиентам перед POST/PUT/PATCH/DELETE нужно получить токен через
`GET /api/session` с заголовком `X-Orchestrator-Client: local-ui`, затем передать
его в `X-Orchestrator-Token`. Токен не заменяет авторизацию задачи. Удалённый
доступ не поддерживается; `ORCHESTRATOR_DEV_ORIGIN` предназначен только для
явного разрешения локального HTTP-интерфейса разработки.
