# Инструкция по созданию Bootstrap Harness v1

Статус: draft для проверки владельцем; реализация не авторизована

Подготовлено: 2026-08-14

## 1. Назначение

Создать отдельный локальный инструмент `project-bootstrap-harness`, который
проводит владельца через стартовое интервью, применяет правила выбранного
профиля AI-assisted System Design and Agent Memory Kit (далее AMK), показывает
полный предпросмотр и только после явного подтверждения создаёт минимальный
набор проектных документов в новом Git-репозитории.

Формула результата:

```text
версионированные правила AMK
+ ответы и решения владельца
+ детерминированные правила Bootstrap Harness
= стартовые документы нового проекта
```

AMK определяет правила grounding, action intent, минимальности и структуры.
Владелец определяет факты, цели, бизнес-гипотезы, ограничения и решения нового
проекта. Harness не имеет права выводить проектные факты из названия каталога,
шаблонов AMK или общих знаний модели.

## 2. Граница продукта

Bootstrap Harness является отдельным продуктом и отдельным Git-репозиторием.
Рекомендуемое расположение:

```text
C:\Alex\Self\projects\project-bootstrap-harness\
```

Связанные системы остаются независимыми:

| Система | Роль |
|---|---|
| AMK | Версионированный read-only источник правил и шаблонов |
| Bootstrap Harness | Интервью, нормализация, preview и создание Core-документов |
| Orchestrator | Исполнение уже понятных и авторизованных implementation-задач |
| Целевой проект | Самодостаточный владелец продуктовых документов и кода |

Harness не должен размещаться внутри репозитория AMK или Orchestrator. Целевой
проект не должен получать runtime-зависимость от любого из них.

## 3. Начальная технология

Для v1 использовать:

- Node.js 20 или новее;
- TypeScript в strict mode;
- CLI без web-интерфейса;
- Draft 2020-12 JSON Schema для закрытых входных и выходных контрактов;
- SHA-256 и канонический JSON для идентичности плана;
- только стандартные файловые и криптографические API Node.js, кроме одного
  поддерживаемого JSON Schema validator;
- тесты через встроенный `node:test` или эквивалентный минимальный runner.

Изменение языка, runtime или UI является отдельным решением владельца до
начала реализации.

## 4. Зафиксированная AMK-база

Первый адаптер должен поддерживать только текущую проверенную локальную базу:

```text
AMK root:
C:\Alex\Self\projects\AI-assisted_System_Design_and_Agent_Memory_Kit

Git commit:
6e6ccbde76d329cfc275ee33bacb7e428cc02be3

Объявленная версия пакета:
v5.0.0

Профиль:
Core
```

Адаптер читает только следующие источники внутри `Agent Kit/kit/`:

| Путь | SHA-256 |
|---|---|
| `ADOPTION_PROFILES.md` | `d7978697abbda3fb040b9eaf5e99ae9ce63205e2bf3b3c7757040ea960fccb5c` |
| `NEW_PROJECT_ADOPTION_GUIDE.md` | `b7c89823bfbd43a62dc22bef6e6576950b50b1879d8c179ef5869d438f0554ce` |
| `PROJECT_GROUNDING_CONTRACT.md` | `06c2520be131c8be90849cec002243051fb7872177e0b41842613b0c0f6b6177` |
| `ACTION_INTENT_CONTRACT.md` | `826a601a9313be25e52e1e0c0faa30b62a8053f2b3a8e65e650adfa322e77123` |
| `AGENTS.md_TEMPLATE.md` | `8d784dceb67ba68fa9c730a1637e962910a6e9deac696f353d323ff1edc87a54` |
| `README_AUTHORING_GUIDE.md` | `a3afe8ee8acc9755c4438f110bc981889c1d79e1a20e6367e3f72a624df64803` |

Harness обязан сверить эти значения с фактическими байтами и с
`Agent Kit/kit/SHA256SUMS.txt`. Несовпадение хотя бы одного источника завершает
операцию до интервью и до любой записи.

AMK нельзя парсить как произвольную прозу с эвристическим извлечением правил.
Адаптер v1 содержит явно проверенное отображение нормативных требований на
поля интервью и секции выходных файлов. Обновление AMK требует новой версии
адаптера и отдельного dry-run review.

## 5. Режим запуска

Основная команда:

```powershell
project-bootstrap start `
  --target "C:\Alex\Self\projects\new-project" `
  --amk-root "C:\Alex\Self\projects\AI-assisted_System_Design_and_Agent_Memory_Kit" `
  --profile core
```

Один запуск имеет четыре фазы:

1. `preflight` — read-only проверка AMK, целевого каталога и Git;
2. `interview` — сбор ответов только в памяти процесса;
3. `preview` — нормализация, полный список файлов, содержимое и hash плана;
4. `apply` — запись только после точного подтверждения владельцем.

Команда с `--dry-run` обязана завершаться после preview и не менять файловую
систему, Git, AMK, Orchestrator или внешний сервис.

## 6. Preflight

До интервью Harness должен доказать:

- `--target` является существующим абсолютным каталогом;
- `--target` является корнем отдельного Git worktree;
- целевой путь не совпадает и не вложен в AMK или Orchestrator;
- каждый запланированный выход остаётся внутри `--target` после разрешения
  существующих родительских путей;
- симлинк, junction или reparse point не позволяет выйти из целевого корня;
- все пять целевых документов отсутствуют либо являются результатом точного
  идемпотентного запуска этого Harness;
- AMK root является ожидаемым Git worktree на зафиксированном commit;
- шесть разрешённых AMK-файлов существуют и имеют точные хеши;
- сеть, credentials и внешние API для запуска не нужны.

Harness не выполняет `git init`, `git add`, `git commit`, `git push`, создание
удалённого репозитория или изменение Git config.

## 7. Контракт интервью

Интервью должно быть коротким, возобновляемым только внутри текущего процесса
и разделённым на четыре блока.

### 7.1 Продукт

- рабочее название проекта;
- кто является предполагаемым пользователем;
- какая проблема решается;
- какой результат получает пользователь;
- ценностное предложение;
- самый маленький полезный результат v1;
- явные non-goals первой версии.

### 7.2 Бизнес

- предполагаемый покупатель или источник финансирования;
- гипотеза модели дохода;
- предполагаемый канал привлечения;
- основные классы затрат;
- какая проверка покажет наличие спроса;
- какие утверждения пока не подтверждены.

Бизнес-поля по умолчанию имеют статус `hypothesis`, а не `fact`. Перевод в
`owner_decision` требует отдельного явного подтверждения владельца. Рыночная
валидация не может быть выведена только из подтверждения владельца.

### 7.3 Ограничения и риски

- бюджет и сроки, если они действительно определены;
- приватность и классы данных;
- допустимые и запрещённые внешние сервисы;
- допустимые side effects;
- юридические, финансовые или безопасностные ограничения;
- критические неизвестные и стоп-условия.

### 7.4 Реализация и проверка

- статус выбора стека: `unknown`, `candidate` или `decided`;
- первый проверяемый пользовательский сценарий;
- способ проверить полезный результат;
- открытые архитектурные вопросы;
- следующий минимальный шаг: исследование, решение или реализация.

Каждый содержательный ответ должен иметь один статус:

```text
owner_intent | owner_decision | hypothesis | constraint | unknown
```

Harness не должен задавать вопрос только ради заполнения шаблона. Необязательная
секция без реального содержания исключается из результата.

## 8. Ограничения входа и приватность

Закрытая схема интервью должна:

- отклонять неизвестные поля и неизвестные статусы;
- ограничивать длину каждого ответа и общий размер интервью;
- запрещать credentials, access tokens, private keys и содержимое `.env`;
- не принимать бинарные вложения, URL для автоматического чтения или пути для
  широкого сканирования;
- не отправлять ответы в сеть;
- не сохранять сырой transcript, отменённые варианты или внутреннее reasoning;
- показывать безопасную ошибку без повторения секретоподобного ввода.

Локальные ответы существуют в памяти процесса до отмены, успешного apply или
завершения процесса.

## 9. Детерминированная нормализация

Одинаковые нормализованные ответы, AMK adapter version и source hashes должны
создавать байт-в-байт одинаковый план, кроме явно исключённого времени в
нехешируемой CLI-обёртке.

Нормализация должна:

- приводить окончания строк к LF;
- удалять незначимые внешние пробелы;
- сохранять смысловой порядок списков владельца;
- сортировать только наборы, где порядок не несёт смысла;
- отличать `unknown` от отсутствующего необязательного ответа;
- не перефразировать утверждения владельца моделью;
- не добавлять архитектуру, стек, бизнес-правило или ограничение по умолчанию.

`planHash` вычисляется по каноническому объекту, содержащему adapter identity,
AMK source hashes, нормализованные ответы, список путей и точные выходные байты.

## 10. Выходные файлы

Успешный v1 создаёт ровно пять файлов:

```text
<target>/
  README.md
  AGENTS.md
  project.bootstrap.lock.json
  docs/
    PROJECT_BRIEF.md
    CURRENT_WORK.md
```

### `README.md`

Содержит только:

- цель проекта;
- предполагаемого пользователя;
- первый полезный результат;
- non-goals v1;
- краткую навигацию по проектным документам;
- текущий статус проекта, например `inception`.

### `AGENTS.md`

Адаптирует Core-правила AMK к конкретному проекту:

- текущая инструкция владельца имеет высший приоритет;
- проектные факты берутся из открытых текущих источников проекта;
- вопросы, анализ, review и plan не разрешают запись;
- запись и внешнее действие требуют явного intent, точной области и проверки;
- гипотезы и unknown не становятся фактами;
- код, тесты и принятые решения побеждают вторичную память;
- новая очередь или автоматизация не создаётся без соответствующего trigger.

Harness не копирует весь `AGENTS.md_TEMPLATE.md`; он создаёт короткий
проектный файл из явно сопоставленных Core-требований.

### `docs/PROJECT_BRIEF.md`

Содержит нормализованные owner intent, бизнес-гипотезы, ограничения, MVP,
критерий проверки, unknowns и non-goals. Статусы должны быть видимы человеку.
Документ не утверждает, что гипотеза подтверждена рынком.

### `docs/CURRENT_WORK.md`

Содержит:

- стадию `inception`;
- одну текущую цель;
- один следующий минимальный шаг;
- блокеры и открытые вопросы;
- критерий перехода к следующей стадии;
- явное указание, что implementation queue ещё не авторизована, если readiness
  gate не пройден.

### `project.bootstrap.lock.json`

Закрытый машинный provenance-контракт содержит:

- contract type/version;
- Harness version;
- adapter version;
- AMK commit и объявленную версию пакета;
- точные относительные пути и SHA-256 использованных AMK-источников;
- profile `core`;
- `planHash`;
- хеш и размер каждого созданного файла;
- owner confirmation kind без имени, переписки и текста ответов.

Lock не является источником продуктовой истины и не содержит сырого интервью.

## 11. Preview и подтверждение

Перед записью CLI показывает:

- точный target root;
- пять точных относительных путей;
- полный Markdown diff/содержимое создаваемых документов;
- redacted summary lock-файла;
- `planHash`;
- список неразрешённых unknowns;
- readiness disposition;
- явные non-actions.

Для apply владелец вводит точное подтверждение:

```text
APPLY <первые 12 символов planHash>
```

Несовпадение подтверждения, изменение target или AMK evidence после preview
отменяет authority. Harness повторяет preflight непосредственно перед первым
write и пересчитывает `planHash`.

## 12. Запись, атомарность и повтор

Apply должен:

1. создать временные файлы только внутри target root;
2. проверить их схему, размер, хеш и отсутствие path escape;
3. повторно проверить отсутствие конфликтующих целевых файлов;
4. переименовать файлы атомарно в фиксированном порядке;
5. при ошибке удалить только временные файлы текущего запуска;
6. не удалять и не перезаписывать пользовательские файлы;
7. вернуть точный bounded receipt в stdout.

Точный повтор с тем же lock и неизменёнными файлами возвращает `already_applied`
без записи. Если lock существует, но хотя бы один managed file отличается,
операция завершается `TARGET_ALREADY_BOOTSTRAPPED` или
`MANAGED_FILE_DRIFT`; автоматическое исправление запрещено в v1.

## 13. Readiness gate и связь с Orchestrator

Harness рассчитывает только advisory disposition:

```text
research_required | decision_required | single_slice_ready | queue_candidate
```

`queue_candidate` допускается только когда:

- пользователь, проблема и первый полезный результат определены;
- MVP и non-goals определены;
- проверка результата определена;
- критические ограничения и unknowns не скрыты;
- известны как минимум две независимо полезные задачи;
- их порядок или зависимости можно определить до исполнения.

Disposition не создаёт очередь и не даёт authority Orchestrator. Harness v1
не пишет в `C:\Alex\Self\projects\orchestrator\queues`, не запускает API и не
создаёт task contracts. Отдельная owner-approved стадия позже преобразует
принятые проектные документы в Orchestrator queue по правилам самого
Orchestrator.

## 14. Стабильные ошибки v1

Минимальный закрытый набор reason codes:

```text
INVALID_ARGUMENT
INVALID_INTERVIEW
SECRET_LIKE_INPUT_REJECTED
AMK_ROOT_INVALID
AMK_COMMIT_MISMATCH
AMK_SOURCE_MISSING
AMK_SOURCE_HASH_MISMATCH
AMK_ADAPTER_STALE
TARGET_NOT_GIT_ROOT
TARGET_SCOPE_ESCAPE
TARGET_REPARSE_ESCAPE
TARGET_FILE_CONFLICT
TARGET_ALREADY_BOOTSTRAPPED
MANAGED_FILE_DRIFT
PLAN_STALE
CONFIRMATION_MISMATCH
APPLY_FAILED
```

Ошибки не должны возвращать полные ответы интервью, содержимое секретоподобной
строки, приватные environment values или широкие локальные пути, кроме явно
предоставленных `target` и `amk-root` в локальном CLI.

## 16. Обязательные тесты

До первого релиза должны проходить тесты, доказывающие:

1. закрытые схемы принимают valid fixtures и отклоняют unknown fields;
2. production adapter содержит ровно шесть разрешённых AMK-источников;
3. текущие AMK-файлы соответствуют зафиксированным хешам;
4. изменение одного байта AMK evidence даёт fail-closed до интервью;
5. одинаковый ввод создаёт одинаковый `planHash` и одинаковые файлы;
6. перестановка смыслового списка меняет identity, а перестановка множества —
   нет;
7. unknown и hypothesis не отображаются как fact/decision;
8. пустые необязательные секции не создаются;
9. dry-run не меняет target, Git, AMK или Orchestrator;
10. неверное подтверждение не создаёт ни одного целевого файла;
11. stale plan после изменения target или AMK отклоняется;
12. path traversal, symlink/junction/reparse escape отклоняется;
13. существующий пользовательский файл никогда не перезаписывается;
14. частичная ошибка оставляет пользовательские файлы неизменными и очищает
    только собственные temp-файлы;
15. точный повтор возвращает `already_applied` без mutation;
16. drift managed file завершается fail-closed;
17. lock не содержит сырого интервью, secrets или environment values;
18. Harness не импортирует сетевой клиент и не выполняет Git mutation;
19. readiness disposition не создаёт очередь и не утверждает готовность как
    authority;
20. Windows paths с пробелами и кириллицей обрабатываются корректно.

## 17. Команды проверки

Проект должен определить как минимум:

```powershell
npm run check
npm test
npm run build
git diff --check
```

Acceptance также включает ручной Windows smoke в новом временном Git-репозитории:

1. dry-run минимального интервью;
2. проверка preview и отсутствия файлов;
3. apply с точным hash confirmation;
4. проверка пяти созданных файлов;
5. точный повтор с результатом `already_applied`;
6. изменение managed file и проверка `MANAGED_FILE_DRIFT`;
7. отсутствие изменений в AMK и Orchestrator.

## 18. Явные non-goals v1

В первую версию не входят:

- web UI или desktop UI;
- LLM-генерация или внешние API;
- автоматическое исследование рынка;
- утверждение жизнеспособности бизнес-модели;
- полный Project Map или Standard/Workflow/Reference Lab adoption;
- task contracts, eval suites, registries или `.work`;
- генерация или запуск Orchestrator queue;
- Git init/add/commit/push и создание GitHub-репозитория;
- обновление существующего проекта;
- автоматическая миграция при обновлении AMK;
- хранение transcript или provider reasoning;
- установка копии AMK в целевой проект.

## 19. Порядок реализации после принятия инструкции

Реализацию начинать только после отдельного явного принятия владельцем. Затем:

1. создать новый Git-репозиторий и минимальный Core handoff для самого Harness;
2. зафиксировать закрытые схемы и AMK adapter identity;

после impact map всех production, test, schema, fixture, manifest, checksum,
documentation и acceptance paths. Неопределённые исследования не помещать в
implementation queue.

## 20. Решение владельца

Требуется отдельное решение владельца по следующим пунктам:

- принять точную AMK commit/hash binding;
- принять пять выходных файлов;
- принять отсутствие Git и Orchestrator mutations;
- принять exact-confirmation и fail-closed overwrite policy;
- после этого отдельно авторизовать подготовку implementation contract или
