# Проверка фактов аудита и однократный контекст

Это явное подключение к существующим `verificationCommands`, а не автоматическая
оценка любого ответа. Старые очереди не меняют формат. Первый поддержанный случай —
read-only аудит заранее известного набора неизменяемых источников.

## Принятое решение: v2 для новых строгих аудитов

Статус: принято владельцем проекта 2026-09-22.

Для новых read-only аудитов с заранее определёнными проверяемыми вопросами,
источниками и случаями покрытия стандартом подготовки является **v2**:

- Используйте [шаблон v2](../templates/audit-v2.prompt.md) и контракт `version: 2`.
- До запуска проверьте авторские ожидания по исходникам и исполняемым примерам,
  зафиксируйте точные вопросы, диапазоны источников и хэш контракта.
- Ответ содержит только `facts`, `coverage` и маркер завершения. Каждая запись
  покрытия содержит `id`, `case`, `evidence`, `status`; свободная проза запрещена.
- Подключайте enabled read-only authorization и обязательную, не advisory,
  `verificationCommand`. Ревью не заменяет машинную проверку.
- Ошибки формата и фактов сохраняются как неудачные попытки вместе с расходом;
  нельзя ослаблять gate или незаметно исправлять ответ ради успешного статуса.

Причина выбора — проверяемость результата: неверные значения, неполные записи
покрытия и свободные утверждения не принимаются как проверенный отчёт.
Это не гарантия полноты аудита и не автоматическое установление истинности
авторского эталона. Снижение общего расхода или денежная экономия **не доказаны**;
они не являются основанием принятого решения.

Открытое исследование, в котором вопросы и границы ещё неизвестны, остаётся
обычным анализом. Сначала определите проверяемый объём здесь, затем готовьте
строгий аудит; не подменяйте неизвестное покрытие статусом `not-covered`.

Решение задаёт стандарт авторинга, а не новый глобальный переключатель runner.
Существующие v1-очереди и сохранённые запуски не мигрируются автоматически;
совместимость v1 сохраняется. Установка Desktop и новые экспериментальные
прогоны для фиксации этого решения не требуются.

## Контракт v1: совместимость с существующими аудитами

В существующей схеме v1 JSON содержит три поля: `version: 1`, `sources`, `facts`.
Для новых строгих аудитов используйте описанную ниже версию 2. Каждый source
имеет точный нормализованный путь относительно рабочего репозитория, SHA-256
исходных байтов и непересекающиеся включительные диапазоны строк:

```json
{
  "version": 1,
  "sources": [{"path": "src/example.ts", "sha256": "<actual 64 lowercase hex characters>", "ranges": [[1, 20]]}],
  "facts": {"trueLabel": "Да", "missing": null, "zero": "0"}
}
```

Ожидания определяет и проверяет автор до запуска, желательно независимыми
исполняемыми тестами. Этот механизм не выводит истину автоматически из хэша.
Контракт и скрипт проверки должны находиться вне `allowedPaths` исполнителя.
Путь к скрипту — точный абсолютный; репозитории внешних скриптов объявляются в
`externalReadRoots` согласно правилам очереди. Не используйте пользовательские
очереди из `queues/` как версионируемую зависимость.

Для пакета контекста выполните:

```text
node scripts/audit-evidence.mjs context contract.json C:\project
```

Команда печатает ASCII JSON с исходными Unicode-символами, представленными
escape-последовательностями без потери данных. Вставьте его один раз в задание.
Дубли пути и перекрывающиеся диапазоны отклоняются, а не молча удаляются.
Не передавайте одновременно этот пакет и копии тех же файлов. Для больших
наборов задавайте только необходимые диапазоны и явно разрешайте дочитывание.
Универсальный автоматический порог размера и запрет непрозрачных внутренних
чтений CLI не реализованы.

## Ответ и обязательная проверка

Исполнитель возвращает один fenced JSON-блок с единственным полем `facts`;
состав полей, значения, типы и пробелы должны точно совпасть с контрактом.
Обычный маркер исхода исполнителя остаётся обязательным.

```json
{"facts":{"trueLabel":"Да","missing":null,"zero":"0"}}
```

В `verificationCommands` укажите одну точную команду (подставьте свои пути и
SHA-256 **всего файла контракта**):

```text
node "C:\orchestrator\scripts\audit-evidence.mjs" verify "C:\project\contract.json" "C:\project" <contract-sha256>
```

Нужны enabled authorization и обычный, не advisory, режим verification.
Runner передаёт `ORCHESTRATOR_RESULT_PATH` — собственный снимок текущего ответа
из каталога запуска. Он обновляется перед проверкой, в том числе после correction.
Унаследованное значение переменной удаляется; preconditions не получают снимок.
Не задавайте эту переменную вручную в очереди и не вычисляйте task/run ID сами.

Изменённый контракт, источник, неверный literal, отсутствующий/лишний факт,
дублирующийся JSON-ключ, неоднозначный ответ, небезопасный путь или превышение
лимита приводят к ненулевому exit code до ревью. stdout содержит детерминированный
отчёт по проверенным фактам, хэшам контракта и ответа, с `narrativeStatus: unverified`.
Он сохраняется существующей verification receipt. Свободное пояснение не
включается в проверенный отчёт; ревьюер обязан отдельно искать противоречия.

Ограничения: до 32 источников, 1 MiB на источник/4 MiB всего, 64 KiB контракт
и ответ, 64 факта; сериализованные факты ограничены 4000 байт для сохранения
полного отчёта в существующей ограниченной verification receipt. Это не JSON
Schema для произвольного результата и не доказательство полноты аудита/UI.
Числа поддерживаются только как безопасные целые JavaScript без `-0`;
точные дроби задавайте строками. Глубина вложенных значений ограничена 32.
Скрипт не пишет в workspace и не выполняет исходный код.

## Расход и диагностика

### Короткий ответ ревьюера

Ревьюер получает исходное задание как объект проверки, а не как собственный
шаблон ответа. При одобрении ему предписана только строка `VERDICT: APPROVED`;
при отказе — `VERDICT: CHANGES_REQUESTED` и конкретные замечания с путями/ID и
противоречащими данными. Повтор JSON, пересказ результата и списки успешных
проверок запрещены инструкцией. Это не жёсткий лимит токенов и не новый parser:
старые сохранённые отчёты остаются читаемыми, фактическое соблюдение и экономию
нужно измерять отдельным прогоном. Замечания нельзя скрывать ради краткости.

### Версия 2: закрытые утверждения о тестовом покрытии

Для строгого аудита используйте `version: 2` и дополнительный обязательный
массив `coverage`. `sources` и `facts` имеют прежний формат. Например:

```json
{
  "id": "localized-display",
  "case": "Отображение известной локализованной сущности в supplied labels.test.ts",
  "status": "covered",
  "evidence": [{"path": "labels.test.ts", "lines": [5, 9]}]
}
```

Каждая запись содержит только `id`, `case`, `status`, `evidence`. Допустимые
статусы: `covered`, `not-covered`, `unknown`. ID уникален, до 64 ASCII-символов
`[a-z][a-z0-9-]*`; `case` — непустое точное определение до 256 символов.
Лимит — 32 записи, до 16 ссылок в каждой; ссылки обязательны и не дублируются.
Путь должен точно совпадать с одним из `sources`, а диапазон целиком входить
в один из его предоставленных диапазонов. Общий ASCII JSON для `facts` и
`coverage` ограничен 4000 байтами, чтобы отчёт помещался в verification receipt.

Автор заранее проверяет ожидаемые статусы и ссылки по тестам и фиксирует хэш
всего контракта в gate. Различайте проверку отображения, прямой вызов фильтра,
косвенный путь через alias map и конкретные варианты `Отчет`/`Отчёт`.
Для `not-covered` перечисляйте весь проверенный набор тестов и явно ограничивайте
им утверждение; неизвестные или непредоставленные тесты — `unknown`, не отсутствие
покрытия. Это не процент statement/branch coverage и не автоматическое доказательство
семантики теста: ошибка авторского эталона остаётся возможной. Хэш подтверждает
байты, а не истинность утверждения. Скрипт не исполняет тесты и не использует модель
для оценки покрытия.

`context` возвращает определения случаев и точные ссылки, но не ожидаемые статусы
или значения `facts`. В задании отдельно укажите требуемые ключи фактов. Ответ v2:

```json
{"facts":{"trueLabel":"Да"},"coverage":[{"id":"localized-display","case":"Отображение известной локализованной сущности в supplied labels.test.ts","status":"covered","evidence":[{"path":"labels.test.ts","lines":[5,9]}]}]}
```

Вне единственного JSON-блока разрешён только один маркер
`ORCHESTRATOR_EXECUTOR_OUTCOME_V1: COMPLETED`. Свободный текст, даже при правильных
фактах, приводит к `AUDIT_UNSTRUCTURED_CLAIM`; неверный/пропущенный/лишний статус,
ID, определение, ссылка или порядок — к отказу проверки. Поэтому неверное обобщение
нельзя спрятать рядом с верными структурированными данными. Проблемы с источниками
следует честно сообщать как остановку, а не подделывать успешный ответ.

Успешный `audit-facts-coverage-matched-v2` отчёт берёт значения из закреплённого
контракта; `coverageBasis: owner-authored-expectations` указывает их происхождение,
`narrativeStatus: not-permitted` — отсутствие свободных утверждений. Команда `verify`
и механизм `ORCHESTRATOR_RESULT_PATH` прежние. V1 по-прежнему допускает непроверенный
свободный текст. Исторические очереди не переводятся на v2 автоматически.

Проверки v2: `node --import tsx --test scripts/audit-coverage.test.mjs scripts/audit-evidence.test.mjs server/audit-result.test.ts`.

### Перенос поведенческих утверждений из прозы

Версионируемый шаблон задания: `templates/audit-v2.prompt.md`. Автор заменяет
`{{QUESTIONS_JSON}}` определениями вопросов без ожидаемых значений, а
`{{CONTEXT_JSON}}` — единственным пакетом источников и `coverageCases` без статусов.
Шаблон явно требует все четыре поля каждой записи: `id`, `case`, `evidence`,
`status`. Поле `case` копируется полностью, а не опускается или пересказывается.
Обязательный gate остаётся отдельной настройкой задачи: сам шаблон его не включает.
Проверка шаблона: `node --test scripts/audit-prompt.test.mjs`.

Для уже известных проверяемых случаев новая версия схемы не нужна: используйте
точные ключи `facts` в v2, а утверждения о тестах — только в `coverage`.
Обобщение «регистр не влияет» замените отдельными вопросами для известного
lookup и неизвестного fallback, например результатами для `FOO_BAR` и `foo_bar`.
Утверждение «source очищает ключ» разбейте на две явно заданные последовательности:
с существующим уведомлением и после dismiss. Для каждого вопроса определите
начальное состояние, операции, наблюдаемое значение и точное ожидаемое значение.
Количество вызовов handler и число видимых уведомлений — разные факты.

Перед исполнением автор проверяет ожидания по закреплённым исходникам и
исполняемым контрпримерам. В prompt передаются определения вопросов и контекст
без ожидаемых ответов; хэш контракта остаётся в обязательной проверке. `context`
не задаёт смысл ключей `facts`: автор обязан явно приложить вопросы к заданию.
Не удаляйте ложную прозу из старого ответа, объявляя остаток исправленным:
её проверяемый смысл должен получить отдельный вопрос, а новый ответ — пройти
проверку целиком. Верные факты с любым пояснением снаружи также отклоняются.

Это закрытый аудит заданных случаев, не автоматическое обнаружение всех ошибок.
Непредусмотренный вопрос требует нового проверенного авторского контракта, а
не расширения ответа исполнителем. Старые очереди и installed-приложение не
мигрируют автоматически; новые пакеты подключаются явно. Нельзя приравнивать
отклонение вручную подготовленных плохих ответов к качеству живой модели или
экономии токенов; для этого нужен отдельный модельный прогон.

Регрессия этих правил: `node --test scripts/audit-claims.test.mjs`.
Она не зависит от пользовательских пакетов в `queues/` и входит в обычное
обнаружение тестов через `npm test`. Проверяются отдельные и совмещённые ошибки,
пропуски/лишние поля, точные значения и запрет свободных утверждений; истинность
данных конкретного внешнего проекта эта регрессия не устанавливает.

### Метрики

Существующий отчёт координации показывает роли и теперь вход без кэша.
Разность считается внутри одной записи, затем суммируется: нельзя вычитать
два неполных итога, полученных от разных наборов наблюдений. Отсутствующие данные
остаются неизвестными; legacy — частичные. Одобрение ревьюера не означает, что
весь результат качественный, поэтому «стоимость корректного ответа» автоматически
не объявляется подтверждённой.

Журнал команд сохраняет `OUTPUT_META`: UTF-8 размер, SHA-256 полного полученного
вывода и признак обрезки. Это позволяет сопоставлять выводы, не сохраняя больше
исходного текста. Одинаковый хэш не доказывает лишнее чтение; метаданные не являются
приёмкой результата и не позволяют восстановить обрезанный текст.

Проверки: `node --import tsx --test scripts/audit-evidence.test.mjs server/audit-result.test.ts server/command-event.test.ts server/coordination-economics.test.ts src/CoordinationReport.test.tsx`.
